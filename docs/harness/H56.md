# H5 and H6 on Fates game records (robot round 7, 2026-11-13)

**In plain words.** The live compare (capture runs A+B) says "the readable code gave the same answer as the game
every time it was asked". It does not say how much of the readable code real play actually ran, nor whether the
records would notice if that code were wrong. H5 answers the first: it replays every kept game record through a
build of the readable code that counts which lines and branches ran (gcov). H6 answers the second: it plants one small
bug at a time in the readable code (a flipped comparison, a constant + 1, the next field read, ...) and replays the
same records; a bug is **caught** when some record then disagrees with the game. These are the F-017 prerequisites
for any writer: a writer may be written only once the replays can catch it. The Awakening port's H5/H6
(its docs/HARNESS.md: route list, verdicts, `harness.py --mutate`) are the reference; the tools here are its
`mutate.py` and `replay.c`, made per-game. Tags: **[high]** checked by a script, **[med]** indirect.

## 6. Round 8 (prep): run folders, any label, faster H6, writer H6, opt-* records [high]

**Run folders.** Every `h56.py h5` / `h6` writes `build/harness/h56/<label>/runs/<id>/` (id: `--run-id`, else the start
time and the command; an existing id is refused). Only a COMPLETE run is copied up to `<label>/h5.json` / `h6.json`
(h5: exact coverage, no harness problem, no bad record; h6: no `--functions`, no `--writer-callees`, no problem), so
a partial run never overwrites `play/h5.json` again; `<label>/latest.json` names the latest complete run and lists
the partial ones with the reason. `h6` reads its MATCH list from `<label>/h5.json` (or `--h5 PATH`).

**Any label.** `--label` takes any name of letters, digits, `_ . -`. A label starting with "cheat" is the cheat track
and accepts cheat-track record folders only; any other label accepts real play only (F-019, never mixed). A record
folder whose route is named `cheat-*` counts as cheat track even when its run.json lacks the flag.

**H6 speed.** `h6` now runs up to `--files-at-once` source files side by side (default `--jobs`), with at most
`--jobs` compiler / replay.exe / gcov processes at once over all of them (`mutate.set_process_limit`), the shared
object cache built once first, and each file's baseline replays side by side. `--files-at-once 1` is the old order.
`--jobs-over-budget` lets `--jobs` go past FEF_ROBOT_JOBS (spare cores; the process stays below-normal). Measured on
the same subset (28 overrides in 9 files, 238 mutants, records of r7-h5; the PC shared with other agents' robot runs,
so seconds are rough):

| Run | Processes | Wall | Result |
|---|---|---|---|
| old order (`--files-at-once 1`) | 2 | 963 s | 172/238 caught |
| new | 2 | 850 s (-12%) | 172/238, every one of the 238 mutant rows (result, by, reached, why) identical |
| old order | 6 | 678 s | identical |
| new | 6 | 539 s (-20% against the old order at 6; -44% against the old default at 2) | identical |

**Writer H6 (plumbing; nothing armed).** `h56.py h6 --writer-callees` mutates only the readable callees of the writer
slots of docs/harness/HOOK_LIST.md (`mutate.writer_callees`: the overrides each slot's game function calls, decoded
from code.bin, plus the overrides named in the slot's "readable callees" cell). On the opt-* records: 5 callees

**In plain words.** H6 used to re-plant and re-replay every bug in every file each time, even in files nothing had
touched. Now `h56.py h6 --cache` remembers each source file's verdicts (caught / survived, by what, reached, why, per
mutant) and reuses them when nothing that could change them has changed. It is **off unless asked**: without
`--cache` or `--no-cache` h6 runs exactly as before.

| Flag | What it does |
|---|---|
| `--cache` | a file whose key is unchanged and whose entry is at most 7 days old is not re-mutated: its rows are written back as this run's `mutants.csv` / `mutate.json` and counted as usual |
| `--no-cache` | every file cold (no hit), every entry refreshed: the weekly clean run, and the run after any compiler or harness change |
| `--cache-dir D` | the cache folder (default build/harness/h56/h6cache/) |
| `--obj-prefix P` | the mutate work folders and object cache are `P-h6...` / `cache-P` (default `game`, as before), so a side run never shares `cache-game` with a live one |

**Key of a file** (tools/harness/h6cache.py), sha256 over: the code of h56.py, harness.py, mutate.py, h6cache.py,
replay.c, replay_abi.h; the compiler's `--version` and `-dumpmachine`; the compile flags and include folders; the
operator set (`OPS_VERSION`, `MUTANT_CAP`); mutants_equivalent.csv; the bytes of the library the original side runs;
the raw source; its **preprocessed** text (`gcc -E -P` with the build's flags, so every header it includes counts); the
preprocessed text of every readable file it can call into, transitively by name, plus all of src/readable/core/ and
replay.c; the overrides mutated (name, address); the mutant list (id, operator, line, column, old, new, mutated text);
and every file of every record folder replayed (name, size, bytes). A hit also needs the entry to be at most
**7 days** old, so each file is re-mutated at least once a week even when nothing changed. A compiler or harness
change changes the key: always a miss. On a miss the summary says which part changed (tools(...), compiler, flags,
operators, equivalents, library, source, headers, deps:FILE, targets, mutants, records, too old). Entries are written
atomically (temp file, then rename). The summary line: `h6: cache: N hit(s), M miss(es), K mutant verdict(s) reused`,
and h6.json `total.cache`.

## 8. Offline capture verdicts instead of a repeat live capture (owner OK C, round 9 speed) [high]

**In plain words.** When only the readable code in the capture library changed, the game itself plays the same
moves, so the calls it makes are the calls already kept in the store-keep records. `tools/harness/offline.py` replays
those kept calls through the new readable code (replay.exe, the same replayer as H5/H6) and writes the same
per-override verdict table a live capture writes. A route or a hook that changed still plays live: the tool decides
which, and prints the parallel.py command for that part.

```bash

python tools/harness/offline.py tree --rev HEAD --name head           # a frozen copy of the sources (build/speed/replay/trees/)

python tools/harness/offline.py compare --offline NAME --live i8-cap  # per route and override against a live capture
python tools/harness/offline.py build-lib --tree build/speed/replay/trees/T   # a scratch library (3dsrecomp, one build at a time)
python tools/harness/test_offline.py                                  # tests (about 20 s; includes offline.py --selftest)
```

**Must play live (the rule, `offline.decide`, tested in the self-test).** A route plays live when its records ran
another input, frames, start save or save_at than routes.json says now; when its start save zip

## 9. H6 sampled mode (owner F-024, round 11) [high for the method; numbers as measured]

**In plain words.** H6 plants one bug at a time and replays the game records to see if any record notices. Round 10
had 106,426 records (2.5 times round 9), and the cache never helps when a round adds records, so a cold H6 would have
taken about 19-20 hours; it was stopped after 7 h 38 min (F-024). Most of those records repeat the same few inputs:
the same override called with the same kind of values, along the same path through the code. The sampled mode keeps,
for each override, a small set of records that still reaches every piece of code the full set reached, plus a few
more with different inputs, and replays the planted bugs on those only.

    python tools/harness/h56.py h6 --sample [--sample-n N] [--budget-min M] [--cache] --sessions S --label play

| Flag | What it does |
|---|---|
| `--sample` | replay a per-override sample (tools/harness/h6sample.py) instead of every record |
| `--sample-n N` | input signatures kept per override (default 64, from the measurement below). The block cover (below) is always kept, even past N |
| `--budget-min M` | any h6 run: stop cleanly M minutes after the start (sampling included). A mutant not started by then is `unjudged` (its row says `time budget`) and not counted; a file not started is listed. The run is then PARTIAL: never published, never cached, and the summary line says how many were left out. With a budget the mutants of each file start in a fixed scrambled order (sha256 of the id), so a cut run's judged mutants are spread over all of the file's overrides |
| `--keep-sample` | keep the sample folders in the run folder (they are deleted at the end otherwise: hard links of game memory) |

**How the sample is chosen** (h6sample.py; rule `cover+fill/2`, part of the cache key):
1. *Trace build*: replay.exe once more, with the readable sources outside src/readable/core/ compiled with
   `-fsanitize-coverage=trace-pc` (GCC calls a hook at the start of every basic block) and tools/harness/h6trace.c
   linked in; replay.c built with `-DFE_REPLAY_TRACE` (the only change to replay.c: two calls and a split `}\n`,
   compiled out of every normal build) adds each record's set of readable blocks run B reached to its JSON line.
2. *Profile*: that build replays every kept record once (one replay.exe per record folder, side by side). The rows
   are matched to the records of records.fecap one to one (count and address checked, else the run stops).
3. *Select*, per override met with a MATCH record: its records are grouped by **input signature** = (block path,
   result r0, the capture's path signature, the replay verdict, the entry arguments r0-r3). First a greedy **cover**: groups are taken, widest
   first, until every block that any record of this override reached is reached by a kept record (a block set also
   tells a taken branch from a not-taken one: the two paths differ by the skipped block). Then **fill**: more groups,
   the least-seen path first, then the least-seen result, until N groups. One record per group: the one whose bytes
   have the smallest sha256, so the choice depends on record content, not on folder names or order. A record whose
   block set overflowed the trace table is always kept.
4. *Sample folders*: one per readable source file, holding the kept records of that file's overrides in sha256 order
   in one records.fecap, their page files hard-linked (copied if a link is refused). Each mutant of the file is then
   replayed on that one folder: one replay.exe per mutant instead of one per record folder.

**Cache key** (h6cache.py): in sampled mode the record folders are replaced by the file's sampled-record digest
(sha256 of the sorted sha256s of its kept records, plus N and the rule). A record names its page files by their hash
and replay.exe checks every page against it, so the digest pins the pages too. The rest of the key is unchanged (the
file's code, preprocessed, every file it can call into, core, the tools, compiler, flags, library, operators, the
7-day limit). So a round that adds records only for overrides of other files keeps this file's sample and hits; a
round that brings new kinds of input for this file's overrides changes the sample and misses (reason `records`).
Sampled entries live in build/harness/h56/h6cache/sampled/, apart from the full-record ones. The key is per source
file, not per override, because a mutant is judged on the records of every override of its file (a caller's record
catches bugs in its callees).

**Output**: `<run>/h6_sample.json` / `h6_sample.tsv` (with `unjudged`, `sample_kept`, `sample_records`,
`sample_signatures` columns and each override's sample numbers); a complete sampled run is copied to
`<label>/h6_sample.json` and noted in latest.json as `h6_sample`. **The full-record `<label>/h6.json` is never
touched by a sampled run**: the two are different measurements and are never mixed in one number.

**Measured on round 10's records** (session r10-capb: 38 real-play routes, 106,426 records; 179 overrides met with a
MATCH record, 175 with something to mutate, 3,396 judged mutants; 27 stillborn). Every run cold (empty cache), `--jobs 6`

**Limits.**
- A sample can miss a planted bug that only a rare record catches: a value gap that one unusual value among
  thousands of records tells apart, in a group the fill did not reach. The cover keeps every *reached block*, so
  "test gap" survivors (the changed line never ran) stay as in a full run; what can grow is "value gap" survivors.
  So the sampled rate is a lower bound of the full-record rate on the same records, not equal to it.
- Block coverage comes from the trace build (-O1 + trace-pc); gcov's line counts (for the `reached` tag) come from
  the sample's own baseline. A branch GCC turns into a select has no block of its own: both sides look like one path.
- One record per input signature. The entry arguments r0-r3 are part of it (rule 2), but arguments are only the
  registers: two calls with the same registers and different game memory behind a pointer are one group. With
  arguments in the signature most overrides have more than N groups, and which N of them the fill takes (least-seen
  path, then least-seen result, then smallest sha256) is a fixed but arbitrary choice among inputs that look alike.
  A pointer argument also makes a new round's records new groups, so such an override's sample (and its file's
  cache entry) changes whenever its own records change.
- The trace build replays every record once per run (about a minute for 106k records at 6 jobs); it is cheap but it
  is not cached.

**Policy (F-024).** H6 no longer runs in every integrate. The sampled run (`h56.py h6 --sample --budget-min 90
--cache --sessions <the round's capture session> --label play`; default N=64, about 43 minutes at 6 jobs on round 10's
records): weekly, and whenever a round's numbers come near the 90% writer gate (F-017, F-021), or before any writer is
armed. The sampled rate is reported as "H6 (sampled, N=64)", never as the full-record number. Run it from a tree
whose src/readable/ compiles (a frozen copy of the round's commit, as above, when other work is mid-edit).
A full-record H6 (`h56.py h6 --no-cache`, no `--sample`) only when a sampled run says the gate is passed (to confirm
it on every record) or when the owner asks; it takes many hours at round 10's record count. A run cut by the budget
is reported as partial with its judged and unjudged counts, never as a measurement of the whole.

## 10. Round 12: H5 first pass in lanes; the offline plan's two lines (Grok's integrate fixes) [high]

Source: docs/collab/INTEGRATE_SLOW_R11_GROK.md sections 2 and 1(a). Host python and the host compiler only; no game.

**In plain words.** H5 replays every kept record folder through a coverage build of replay.exe. Until round 11 it
did this one folder at a time, even when asked for more jobs, because all runs wrote their coverage counters into
one folder, and several programs writing one counter file at once would mix the counts. Now each "lane" gets its own
counter folder. Several folders replay side by side, one per lane, and at the end GCC's own merge tool
(`gcov-tool merge`) adds the lanes' counters together. Then the coverage is read once, as before.

    python tools/harness/h56.py h5 --sessions S --label L [--jobs N] [--merge auto|gcov-tool|python] [--no-exact]

- `--jobs N`: lanes (default and cap: FEF_ROBOT_JOBS, else max_parallel_runs in config/harness/resources.json;
  `--jobs-over-budget` takes N as given). `--jobs 1` is the old serial path, counters straight into the build's
  obj folder.
- Each lane is a folder `<run>/lanes/laneNN/`. replay.exe gets `GCOV_PREFIX=<lane>` and `GCOV_PREFIX_STRIP=99`,
  so libgcov writes `<lane>/<object>.gcda` (all leading folders cut; tested on MinGW). One replay holds a lane at a
  time, so a lane's files are never written by two programs at once. Each record folder is still replayed by only
  one program (the round 9 rule: two h56 runs on the same session at once still collide).
- Merge: `gcov-tool merge` (beside the host gcc, `C:\msys64\ucrt64\bin\gcov-tool.exe`), lane after lane, result
  copied into the build's obj folder next to the .gcno files; then gcov reads it as one run. `--merge python` (and
  the fallback when gcov-tool is missing): gcov reads each lane on its own and python adds the line, branch and
  function counts (`add_cov`).
- The per-override exact pass (no `--no-exact`) is unchanged and still serial. Grok's advice stands: keep it weekly
  or limit it to the new names. It is not on the integrate path.
- h5.json `total` now also holds `lanes`, `counters` (how they were merged), `replay_seconds`, `merge_seconds`,
  `gcov_seconds`, and the run prints one line `h5: first pass ... in N lane(s): replay X s, counters ... Y s,
  gcov Z s`. The per-folder lines and the final `h5 (label): ...` line are the same as before (check_all reads them).

**Self-test (h56.py --selftest, 39 checks).** A tiny program built with --coverage runs three times into one counter
