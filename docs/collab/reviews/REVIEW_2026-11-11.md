# Review, 2026-11-11 — tables, routes, mods, play

ELI5 / ETA: This is a second read of the tools that install mods and back up the save, looking for ways a file could be lost. Nothing was changed. Claude checks these and fixes them. About a short read, already done.

Read at commit `f6dd2ec` and the tree that contains it (working copies of these four areas were clean). No game file opened. No tool edited.

## Findings

### 1. A crash during install can hide the previous file — high

`tools/mods/mods.py`, install, the loop that starts at the move-aside (about line 1463).

What breaks: the previous file is moved into the backup folder before the manifest records that move. The comment above install says a crash leaves nothing uninstall cannot clean up. That is not true for this gap. If the copy fails after the move (disk full is enough) the old file sits in the backup folder and is not in the manifest. Uninstall does not put it back.

How to see it: install when that romfs path already exists. Stop the process after the move-aside and before the manifest write. Run uninstall. The old file is still only in the backup folder.

Fix: record the backup path in the manifest before the move, or move only after that line is written. Uninstall must restore a backup the manifest names even if the new file never appeared.

### 2. A refused uninstall makes the next install refuse too — medium

`tools/mods/mods.py`, uninstall about line 1399, install about line 1466.

What breaks: uninstall leaves a file whose bytes changed since install, and leaves the backup beside it. The next install sees that backup path and stops, telling the owner to move it. The old file is not deleted. A non-technical owner is stuck, and the error does not say "your previous file is safe in this backup folder; uninstall did not restore it."

How to see it: install, change the installed file, uninstall, install again.

Fix: the error should name the backup as the previous file and say it was not restored because the installed file changed. Do not require the owner to guess.

### 3. "Is Zakuro running?" can miss it — medium

`tools/play/play.py`, `zakuro_running`, about line 358.

What breaks: if `tasklist` fails, the check continues and can return false. PLAY then starts a second copy on the same save. The start path itself says two copies can lose progress. The check fails open.

How to see it: make `tasklist` fail (or time out) and start PLAY while Zakuro is open.

Fix: if the check cannot run, stop, and say so. Do not start.

## Checked, not a finding

- Save zips are written to a `.zip.tmp` and renamed into place (`play.py` `zip_save`). A crash leaves the temp file, not a half-written zip at the real name.
- Automatic backups skip when the save's fingerprint matches and that zip is still there. Pruning removes only `auto-*.zip`. Manual and pre-migrate zips are kept.
- Save folders use the same uppercase title id Zakuro writes (`{program_id:016X}` in Zakuro's host archive). The lowercase fallback is only for the mods folder. A missed save from letter case is not the bug it looked like.
- Person rows cannot be appended (`config/tables/appends.csv` policy refuse). Item and Job can, only with the required prefix and number, and the mod build calls `check_table` before staging. A refused append does not write a file.
- Staging deletes the stage folder and writes a new manifest only after the files are written. A crash there makes install refuse ("staged file missing"), it does not install a mix.
- The route tool fails closed if it does not see the three folder letters. A missed register overwrite could pair a label with the wrong letter, but it would not silently accept a missing letter. Not a save-loss bug. The letter map stays the code reading's, not this review's.
