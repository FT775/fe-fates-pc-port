# Our Zakuro patch series

Zakuro (github.com/fearkov/zakuro, MIT) is used at the pin in `config/upstream.json`
(`c856685`, v0.2.32) plus the patches in this folder. Nothing else changes Zakuro.
`tools/engine/engine.py apply` turns them into commits on the local branch `fe14` of
`engine/zakuro` (gitignored), and `engine.py build zakuro` builds that. See
[docs/ENGINE.md](../../docs/ENGINE.md).

**Edition** (round 83, docs/SEAL_EDITION_PLAN.md section 3): which edition a patch is for. ### Why 0003 and 0004 stay in the Fates series

Checked by reading the patch text and the patched source in `engine/zakuro` (2026-11-10):

- Every Awakening part is behind one of two gates, both keyed by title id:
  `game_ui::is_awakening(id)` = `matches!(id, 0x0004_0000_0009_F100 | 0x0004_0000_000A_0500)`
  and `game_ui::for_game(id)` = `is_awakening(id).then_some(&AWAKENING)`.
  - `loader.rs` and `System::set_game_screens` set `system.game_ui` from `for_game`, so
    for Fates it is `None`; no marker list reaches the GPU, so 0001's watch stays empty.
  - `System::follows_cursor()` is `game_ui.is_some() && ...`, and the frontend's
    `extras_active()` needs it. Keys (E, the stick click), the pointer, the layouts, the
    banners and the cursor hiding all check `extras_active()` first.
  - The "Top-screen extras" block in "Settings for this game" is drawn only when
    `is_awakening(program_id)`. Even a hand-edited `[per_game.0004000000179800]`
    `battle_ui`/`bottom_over`/`touch_pointer` only sets `Config::game_screens`, which
    `for_game` then ignores.
  - `sounds::bottom_screen` looks its archive up by title id; Fates has no entry, so it
    reads nothing.
- The one change Fates players see: the general settings' Controls list gets the two
  bindings `bottom_over_key` / `bottom_over_button`, which do nothing for Fates.
- Keeping them means one engine (one patch series, one patched Zakuro) for both ports,
  and Fates' own top-screen extras later become one more `GameUi` entry in `for_game`
  plus a `BOTTOM_SCREEN_SOUNDS` entry (`sound/IRON15_sound.bcsar`; the sound names are
  not known yet), instead of a second copy of the mechanism.
- Dropping them is possible and was tried: 0001 + 0002 + 0005 apply cleanly on the pin
  with `git am --3way` (scratch clone, 2026-11-10). If the owner prefers the smallest
  engine, delete 0003 and 0004 here (renumbering is not needed: `apply` takes any
  `NNNN-*.patch` in name order) and run `engine.py apply`.

## Convention

- **Name:** `NNNN-short-topic.patch`, four digits, applied in name order (`0001-...`,
  `0002-...`). Exactly what `git format-patch` writes. Other files here are ignored.
- **One topic per patch, small and file-scoped**, so moving the pin is a mechanical rebase.
- **Format:** `git format-patch --zero-commit --no-signature` output (mail header,
  subject, message, diff), LF line endings. `.gitattributes` should mark `*.patch -text`
  so git never rewrites them (the Awakening repo has it; this repo has no .gitattributes
  yet, see docs/ENGINE.md section 9).
- **Message:** what it changes and why, the facts it relies on (title ids, addresses)
  with their source, and how it was checked.
- **Only our code, or MIT code with its notice.** Code adapted from fe-awakening-recomp
  (github.com/Zelkin1/fe-awakening-recomp, MIT, Copyright (c) its authors) keeps a credit
  line in the patch message and in the source comment, and its licence notice travels
  with it (in the patch, or in a file the patch adds). Zakuro's own MIT notice stays as is.
- **Never** anything from 3dsrecomp (no licence: used unmodified, never copied), and never
  game bytes, text, pictures or generated code (D-003). Addresses and our own logic are fine.

## Making or changing a patch

```
python tools/engine/engine.py fetch          # engine/zakuro at the pin
python tools/engine/engine.py apply          # branch fe14 = pin + this series
cd engine/zakuro
# edit, build (python tools/engine/engine.py build zakuro), test, then commit:
git -c user.name=you -c user.email=you@localhost commit -am "Short topic: what and why"
# write the whole series back out (renumbers from 0001):
git format-patch --zero-commit --no-signature -o ../../patches/zakuro c856685cc867bc6d4ac0f765844ca037ae735941
cd ../..
python tools/engine/engine.py apply          # prints "unchanged": the series matches the branch
```

To change an earlier patch, use `git rebase` on the `fe14` branch, then
format-patch again and delete patch files that are no longer written. `apply` compares
the branch with the series by `git patch-id --verbatim` (whitespace counts, so even a
whitespace-only edit to a patch is re-applied; commit-message-only edits are not, they do
not change the tree): it does nothing when they match,
and otherwise resets `fe14` to the pin and re-applies the series. It refuses to drop
uncommitted edits unless given `--force`. When a patch does not apply, the branch is left
at the pin and the error names the patch.

## Moving the pin

Change `config/upstream.json`, run `fetch`, then `apply`. Patches that fail get rebased
by hand on the new pin and written out again. If a patch or the build fails, the pin
does not move (PORT_PLAN.md section 8).
